| XTPU-0052 | open | high | l | XTPU-0053 | The applet cannot report a job outcome because it consumes none of the runtime's result surface. | XTPU-0053 | open | high | m | XTPU-0052 | The applet calls only `ApplyCommand` (`lib/cinnamon-runtime.js` `CONTROL_METHOD`). `SubmitJob`, `CancelJob`, `DescribePlugins`, and `GetJobResult` are exported by the service and never called, and the applet ships no mirror of `runtime-job-submit`, `runtime-job-cancel`, `runtime-job-acknowledgement`, `runtime-job-result-request`, `runtime-job-result`, or `plugin-inventory`. Nothing in the applet can start, cancel, or observe work; it is a policy editor over a service that can run jobs. |
| XTPU-0054 | open | high | m | — | Nothing can grant the permissions the service's policy gate requires. `src/omnitensor/plugins/policy.py` refuses with `consent-missing` when a required permission has no active grant, but at audit time `plugins/grants.py` `GrantLedger` was never constructed by the service and had no default path, CLI entry point, environment variable, or D-Bus method, and `runtime-command.schema.json` `operation` is closed over `set-profile-enabled, set-profile-weight, set-paused`. The applet has no grant UI or storage. Needs a grant interface agreed with OmniTensor before any applet work; currently latent only because no bundled manifest declares `permissions`. |
| XTPU-0065 | open | medium | s | XTPU-0052 | Cross-repository, owned by OmniTensor. Re-verified against `omnitensor/src/omnitensor/service.py` and `plugins/orchestration.py`: `SubmitJob` now dispatches through `RunnerBackedDispatcher(self.runners, ...)`, `build_plugin_runners` is called with `deliver=` and `progress=`, and `_describe_plugins` passes `granted_permissions`, so three of the four audited defects are gone. What remains is deliberate rather than defective: `_default_dispatcher` still returns `UnavailableJobDispatcher` unless an artifact root is configured, because nothing can prove an unverified model file matches the manifest. Applet-side job work is therefore unblocked by this row and gated instead on XTPU-0069 (no bundled workload declares a model) and on the submission-payload decision in XTPU-0053. |
| XTPU-0066 | open | low | s | — | No version handshake with the runtime service. The applet now diagnoses `UnknownMethod` and the `method-unknown` refusal after the fact, but it still cannot state which contract version the running service speaks before calling it. A handshake needs a service-side version method or property agreed with OmniTensor; D-Bus introspection alone would only enumerate method names. |
| XTPU-0067 | open | low | xs | — | `lib/workload-manifest.js` treats an own property whose value is `undefined` as present, so `requirements.acceleratorPreference: undefined` and `requirements.model.sha256: undefined` are rejected while the authoritative schema treats both as absent. The plug-in subtree already uses the `declared` helper; the requirement predicates still use `Object.hasOwn`. Unreachable from `JSON.parse` output, so it is a mirror-fidelity defect rather than a live failure. |
| XTPU-0068 | open | low | xs | — | Cross-repository documentation gap left by XTPU-0062, owned by OmniTensor: `omnitensor/docs/installation.md` never mentions the shared snapshot path or `OMNITENSOR_STATE_PATH`, so an operator who moves the file has nothing to read. The applet side now pins the agreed default and cross-checks `DEFAULT_STATE_PATH` wherever both checkouts are present (`tests/contract/runtime-state-path-contract.test.js`). |
| XTPU-0069 | open | medium | l | XTPU-0049 | Needs a product decision, not applet work: eight of the nine bundled workloads declare `requirements.model: null`, so `omnitensor/src/omnitensor/plugins/orchestration.py` refuses to build a pipeline for any of them (`profile-has-no-model`) and the ninth stays disabled pending XTPU-0049. The popup now states this per profile, but the catalog still ships nothing the runtime can execute. Decide which workloads get models, in which formats, before any of them can be more than a policy row. |
